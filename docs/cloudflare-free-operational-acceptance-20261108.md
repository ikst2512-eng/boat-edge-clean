## 2026-11-08 — GitHub 2026 run-details dispatch evidence (Draft-only safety upgrade)

**GitHub public API improvement, released 2026-02-19:** Passing `return_run_details: true` alongside `ref: "main"` to `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` permits a **200** response containing `workflow_run_id`, `run_url`, and `html_url` (supported even under `2022-11-28` version). Without this flag, GitHub continues to return legacy **204 No Content**, which cannot independently correlate a run ID. Sources: [GitHub changelog 2026-02-19](https://github.blog/changelog/2026-02-19-workflow-dispatch-api-now-returns-run-ids/) and [GitHub REST workflow dispatch](https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28#create-a-workflow-dispatch-event).

The **recovery-capable** Draft entrypoint now sends `{ref:"main",return_run_details:true}` when the existing opt-in gate is explicitly `"true"`. It accepts only HTTP 200 with a positive safe integer `workflow_run_id` and **exact** expected repository-specific GitHub API and browser run URLs. The accepted receipt records `github_run_id_reported` and `github_run_url_reported`, while preserving `github_run_id_proven:false`, `new_forecast_saved_proven:false`, `formal:false`. **No new read/poll or source-write behavior** is introduced, and external GET/POST count remains 4+2 per fully eligible tick.

- If GitHub returns 204, the workflow **may actually have been dispatched** but no run ID was provided. This is `github_dispatch_accepted_without_run_details` and **must not trigger an automatic retry** from the same invocation. The operator must inspect GitHub independently before any action. A 204 is not a successful auditable run receipt.
- HTTP 200 with missing/malformed/foreign-repository run ID or URLs is `github_dispatch_run_details_missing_or_invalid` and is also an **ambiguous potential dispatch**, not proof of a safely recoverable failure. No second POST should be made speculatively.
- 401/403/404/429/500/503 or transport exceptions likewise remain errors, never formal publication proof.
- Even a **genuine** 200 with a run ID only proves GitHub *reported an enqueued run*. Independent evidence must later verify `GET /actions/runs/{id}`: `workflow_id`, `event=workflow_dispatch`, `head_branch=main`, conclusion/status, immutable first-add prediction SHA, and original pre-T−12 data. None of these GETs or source checks is performed by the Worker. Never call the job or prediction successful from a 200 alone.

**Cross-provider race still OPEN:** GitHub's native `concurrency` serializes workflow executions, but does **not** provide an atomic reservation before simultaneous external POSTs. Direct inspection of the current `main` workflow YAML shows CLEAN uses `cancel-in-progress:false` with the default single pending queue; another incoming dispatch can replace a pending native schedule run. Four-mode instead has `queue:max` with up to 100 pending entries. Neither configuration proves exactly-once capture. Source: [GitHub official concurrency docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency). This PR intentionally **does not change** main GitHub workflow concurrency, source collection, Render or schedule definitions. Propose any cross-provider protocol under a separately reviewed plan.
